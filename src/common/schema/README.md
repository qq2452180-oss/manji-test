# 当前版本数据库结构

这里保存按编号执行的数据库 SQL。0001–0008 是原始建表基线；已发布文件保持不变，后续字段和表通过新增编号 SQL 增量升级。

| 模块 | 执行顺序及文件 | 用途 |
| --- | --- | --- |
| 账号 | `account/0001_users.sql` | 用户、登录凭证、体验身份 |
| 访谈 | `interview/0002_interview_sessions.sql` | 会话、完整消息上下文、消息编号约束 |
| 访谈 | `interview/0003_media.sql` | 图片归属和文件路径 |
| 记忆 | `memory/0004_user_profiles.sql` | 用户画像 |
| 记忆 | `memory/0005_life_events.sql` | 经历索引 |
| 内容 | `content/0006_chapter.sql` | 章节名称、排序及启用状态 |
| 内容 | `content/0007_story.sql` | 故事、摘要、章节关联及记忆处理状态 |
| 内容 | `content/0008_topic.sql` | 话题名称、必填简短说明、所属章节、排序及启用状态 |
| 内容 | `content/0009_story_revisions.sql` | 故事版本和更新时间、补充快照与独立处理进度 |
| 内容 | `content/0010_biography.sql` | 每个用户的传记全文和更新时间 |
| 访谈 | `interview/0011_rtc_calls.sql` | 旧通话元数据表；保留迁移历史，当前 RTC 不使用 |
| 账号 | `account/0012_sms_login.sql` | 用户表增加可为空且唯一的手机号 |

| 内容 | `content/0014_decade_catalog.sql` | 主人公出生年代、分年代的卷名与话题小节 |
| 内容 | `content/0015_occupation_topics.sql` | 职业补充话题的用户归属，公共话题保持不变 |

按全局文件编号执行，不能按模块名称排序。会话建表文件同时创建消息编号校验函数；故事依赖用户、章节和经历表，话题依赖章节表。章节和话题使用自增整数编号，不设 `code` 字段；话题不保存固定开场问题或参考追问。

## 初始化与检查

在项目根目录运行，使用已安装项目依赖的 Python：

```sh
python src/tools/run_sql.py init --database manji_v2
python src/tools/run_sql.py check --database manji_v2
```

工具读取 `src/.env` 的 `DATABASE_URL`（运行环境优先）。`--database` 沿用主机、端口和账号，只替换本次连接的数据库名，不修改配置文件。目标数据库须事先创建，并允许该账号建表。

`init` 在同一事务内建立全部结构和 `src_schema_migrations` 初始化记录；失败时整体回滚。相同文件重复初始化不会重建表。`check` 只读校验记录和全部业务表的必要字段。已有登记数据库运行 `migrate`，先检查已安装文件的校验和，再以事务追加未安装的编号 SQL。0009 不重建故事或访谈，不改变已有正文和来源；现有故事从版本 1 开始。

部署工具还会调用只读 `plan`，校验已有迁移历史并列出待执行编号；数据库已经是最新版本时，也检查必要业务字段。空库只返回计划，不建表；未登记的非空库会被拒绝。在已配置运行环境 `DATABASE_URL` 的终端或应用容器中，可以直接运行：

```sh
python -m src.common.migrate plan
```

该模块命令仅使用环境变量，不自动加载 `src/.env`。输出包括 `pending_versions`、数据库名及实际连接的服务器地址和端口，部署脚本用它核对备份目标，不输出账号或密码。

0010 只创建 `biography` 表，不修改已有故事和访谈，也不调用模型。用户明确结束并要求成文后，业务流程读取旧传记、融合本次故事并保存全文。已有用户首次融合时，以现有故事组成初始旧稿。

0011 创建的 `rtc_calls` 表已停止使用，SQL 文件保留以兼容已登记的迁移校验和。当前 RTC 只在单进程内存中管理通话，消息由现有访谈服务保存；重启后重新拨打，不恢复旧通话。就绪检查不再要求 `rtc_calls` 表存在，本次代码清理不删除已有数据库中的表或数据。

基线 SQL 不预置业务数据。初始化后的业务表均为空，包括章节和话题表；目录内容单独导入。

0012 在 `users` 表中增加 `phone_e164` 字段，按 E.164 格式保存已验证的手机号，每个号码对应一个账号。已有账号的手机号默认为空。验证码与发送限频记录保存在当前后端进程的内存中，重启后用户可重新获取验证码。

0013 为已有正式账号的有效凭证保留从迁移执行时起算的 30 天过渡期。新登录凭证和升级为正式账号的凭证从签发或升级时起有效 720 小时。查询不会续期，同账号再次登录会立即替换旧凭证。旧游客凭证沿用原访问范围。上线时先执行 `migrate` 和 `check`，再切换应用。旧应用在过渡期间签发的凭证也会由数据库设置期限，只有新版应用执行鉴权时会检查到期时间。浏览器通过同源 HTTPS 使用持久会话 cookie，本地回环地址可使用 HTTP 调试。

已打开标签页中仍有效的正式账号 Bearer 凭证可通过同源 `POST /api/auth/session/upgrade` 一次性交换为新的 30 天浏览器会话。交换会替换数据库摘要。旧凭证立即失效，新 cookie 凭证无法再次通过该接口续期。

## 随应用发布自动升级

现有 [部署入口](../../../deploy/production/README.md) 已接入数据库操作。本次使用前，先在本机执行 `./deploy.sh init`，把生成的 `.release/server-setup.tar.gz` 上传到服务器 `/root`，按提示解压并运行 `install-server.sh`，更新服务器上的部署脚本。普通 `publish` 不会替换服务器脚本；之后日常只需本地提交代码并执行 `./deploy.sh publish`。

服务器用新镜像运行 `plan`；有待执行 SQL 时，先备份应用实际连接的现有数据库，再执行 `migrate` 和 `check`，最后切换应用。没有待执行版本时跳过备份与迁移，仍执行检查。沿用服务器 Compose 的环境变量及数据卷，不上传本地 `.env` 或导入本地业务数据，也不重建 PostgreSQL 和网关容器。目标数据库仍须已存在。

数据库备份保存在服务器 `/root/manji-src/deploy/src/database-backups/`，为 PostgreSQL custom 格式，目录权限 `700`、文件权限 `600`。脚本检查归档可读性，不代替恢复演练；图片等媒体文件不在数据库备份中。备份失败会在执行 SQL 前停止。SQL 失败时整个迁移事务回滚；进入迁移阶段后发生的失败会保留 `database-upgrade.json` 和备份，`./deploy.sh status` 的 `database_upgrade_pending` 会显示恢复记录，可重试已上传的同一发布包或发布修复版本。

跨结构版本的应用回滚会被阻止，数据库也不会自动恢复。旧镜像的结构校验会拒绝新版数据库，且旧目录逻辑不具备个人职业话题的访问限制，不能通过放宽检查强行回滚。涉及迁移的发布成功后会清空兼容上一版记录；后续相同结构的应用发布仍可回滚。数据库升级和应用切换之间可能短暂出现就绪检查 503，切换会中断语音通话，具体操作和恢复步骤见部署说明。

## 后续修改

0014 不改写已有章节、话题或故事。新版本上线前执行 `migrate` 和 `check`。某一年代首次被选择时，服务从镜像内的 `src/data/{50,60,70}.md` 读取对应模板，在同一事务内建立该年代目录并保存账号选择；之后所有账号复用这些目录 ID。编辑模板文件不会覆盖已导入的目录；已上线的目录调整请使用增量更新，保留故事和会话引用的 ID。

0015 为 `topic` 增加可空的 `owner_user_id`。已有话题保持公共，新生成的职业话题仅所属用户可见、可选。用户已选择出生年代后，调用 `CatalogService.append_occupation_topics(user_id, yaml_text)`，传入模型返回的 YAML 文本，返回追加后的个人目录。输入沿用 `full_biography_by_decade → decades → sections → topics`，只列新增题；卷和小节必须已存在，不设固定条数上限。生成时由模型根据职业和现有目录的空缺决定数量，要求语义不重复、不凑数量，没有合适新题时可返回空清单。后端跳过完全相同的标题和描述，包括本批重复及重复提交；错误会直接抛出，整批不写入。此入口不调用模型，也不改写模板文件。

0016 在 `users` 保存 `occupation` 和 `occupation_topic_keys`。确认年代和职业后先返回基础目录，职业补题在当前进程的后台线程中执行，通过 `call_qwen_thinking` 生成 YAML，默认思考强度为 `high`，本次模型超时为 1000 秒。模型生成不占用数据库事务；写回时才锁定用户行，重新核对年代、职业并去重追加。成功追加（包括没有新题）后记录组合，同一组合的进行中任务和已完成结果会复用，失败可再次提交重试。目录接口通过 `occupation_status` 返回生成状态，失败时附 `occupation_error`；前端生成中轮询，完成后更新目录。任务状态只保存在进程内存，不做任务持久化或重启恢复，重启后可重新提交。其他用户的目录保持独立。上线前先执行 `migrate` 和 `check`。

已安装的 SQL 不再修改；新增结构放入连续编号文件。`migrate` 校验历史并仅执行新增文件，整个升级失败会回滚。已有库升级前备份，在隔离测试库验证旧数据和重复执行；`check` 要求结构与完整迁移记录一致。工具不接管未登记的非空数据库。

```sh
python src/tools/run_sql.py migrate --database manji_v2
python src/tools/run_sql.py check --database manji_v2
```

需要手工执行单张表时，可运行 `python src/tools/run_sql.py` 交互选择，或指定 `--file memory/0004_user_profiles.sql`。单文件模式不记录整库初始化状态，`check` 需要通过 `init` 完整初始化的库。
